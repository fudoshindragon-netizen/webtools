The JavaScript interview questions that keep coming back — and how to answer them out loud

A handful of concepts recur in almost every JavaScript interview. Here they are, each written as an answer you would actually say in 90 seconds, with the follow-up question that comes next and the trap inside it.

Version 1.0 · Written 2026-11-14 · Study aid — not a hiring guarantee, not affiliated with any employer

JavaScript interviews repeat themselves, and not out of laziness. A small set of concepts separates people who have used the language from people who understand it, and every one of those concepts shows up in real bugs. So the same handful of questions comes back — and the interview is won or lost on how you say the answer, not on whether you have read it.

Below are the eight that recur, each written as an answer you would actually say out loud in 60 to 90 seconds, then the follow-up that usually comes next and the trap inside it. All the questions and answers here are our own wording.

Why these eight keep coming back

Closures, this, the event loop, promises versus async/await, hoisting, == versus ===, array methods and prototypes. Between them they explain most of the JavaScript bugs that reach production: a stale value captured in a loop, a lost this in a callback, a request that runs after the component has gone, a comparison that is true when you did not expect it, a sort that quietly mutates the array.

Interviewers ask them because a definition can be memorised but a follow-up cannot. That is the whole shape of the exercise: give a clean answer, and be ready for one step further.

The eight, answered out loud

1. What is a closure?

Say this: "A closure is a function together with the variables it had access to where it was defined. The function keeps those variables alive after the outer function has returned, so it can still read and write them. A counter is the standard example — the count variable is not global, but the returned function can still increment it, and nothing else can touch it."

The follow-up: "What happens if you create functions inside a loop?"

The trap: with var, every callback shares one binding, so they all see the final value. With let, each iteration gets a new binding, so each callback sees its own. Say both halves — naming let without explaining the shared binding sounds like folklore.

2. How does this work?

Say this: "It depends on how the function is called, not where it was defined. Called as a method, it is the object before the dot. Called as a plain function, it is undefined in strict mode and in modules, and the global object in sloppy mode. Called with call, apply or bind, it is whatever you pass. Called with new, it is the new object. Arrow functions are the exception: they take this from the enclosing scope and cannot be rebound."

The follow-up: "So what does this print inside a setTimeout in an object method?"

The trap: setTimeout calls the callback as a plain function, so this is lost — you get undefined in a module and the global object in a script, not the object. The fixes are an arrow function that captures the outer this, or .bind(this). Say the failure mode, not just the fix.

3. Explain the event loop

Say this: "JavaScript runs one thing at a time on a call stack. Anything asynchronous — a timer, a network response — comes back through a queue. There are two queues that matter: the macrotask queue for timers and I/O callbacks, and the microtask queue for promise callbacks and queueMicrotask. When the stack empties, the entire microtask queue drains before the next macrotask runs. That is why a resolved promise always runs before a zero-millisecond timeout."

The follow-up: "What order does this log — a console.log, a Promise.resolve().then, and a setTimeout(fn, 0)?"

The trap: "zero milliseconds" does not mean immediately; it means "next macrotask". Answer with the order and the reason in one sentence: synchronous first, then the promise callback, then the timer.

4. Promises versus async/await

Say this: "A promise is a value that represents a future result, with three states — pending, fulfilled, rejected — and then, catch and finally to attach work to it. async/await is syntax over the same thing: an async function always returns a promise, and await pauses that one function until the promise settles, without blocking anything else. Same model, readable control flow."

The follow-up: "How would you run three requests at the same time with async/await?"

The trap: writing three awaits in a row runs them one after another. Start them first, then await together: Promise.all for "all or nothing", Promise.allSettled when one failure should not lose the other results. Also mention that a missing await inside a try block will not be caught by that catch — a real bug and a favourite follow-up.

5. What is hoisting?

Say this: "Before a function runs, its declarations are processed. var declarations are hoisted and initialised to undefined, so reading one before its line gives undefined. let and const are also hoisted but sit in a temporal dead zone until their line runs, so reading one throws a ReferenceError. Function declarations are hoisted with their body and can be called earlier. Function expressions and classes are not callable before their line — the class name is in the dead zone too."

The follow-up: "What does typeof x print before let x?"

The trap: with var it prints "undefined"; with let it throws. The trick is that typeof is the one operator that normally does not throw on an undeclared name — the dead zone makes it throw anyway, and that is the point being tested.

6. == versus ===

Say this: "=== compares type and value with no conversion. == converts first, following the coercion rules, which is why 1 == "1" is true and null == undefined is true. I write === by default; the one place == earns its keep is x == null, which is a deliberate check for null or undefined in one go."

The follow-up: "Is [] == false true?"

The trap: it is true — the array becomes an empty string, the empty string becomes 0, and false becomes 0. Answer it, then say you would never write it. The question is testing whether you know the rules, not whether you use them.

7. Array methods

Say this: "map returns a new array of the same length; filter returns a shorter one; reduce folds to a single value; forEach returns undefined and is for side effects; find returns the first match, some and every return booleans. The two that bite: sort mutates in place and sorts by string by default, so [10, 9, 1].sort() gives [1, 10, 9] — you need a comparator. And slice copies while splice mutates."

The follow-up: "Implement map using reduce", or "what is the difference between find and filter?"

The trap: mutating the array you are mapping over, and forgetting the comparator in sort. If you are asked to implement map with reduce, say the accumulator is the new array and the callback pushes into it — then mention you would not do that in real code, because map exists and is clearer.

8. Prototypes

Say this: "Every object has a link to another object, its prototype, and property lookup walks that chain until it finds the property or reaches Object.prototype. Classes are syntax over the same mechanism: methods on a class go on the prototype, which is why they are shared rather than copied per instance. instanceof walks the chain to answer."

The follow-up: "What is the difference between prototype and __proto__?"

The trap: prototype is a property that functions have, used when the function is called with new. __proto__ — better written Object.getPrototypeOf(obj) — is the link of an actual object. Arrow functions have no prototype and cannot be constructors. Getting this backwards is the most common wrong answer in the set.

The follow-up that follows every answer

Notice the pattern above: after the definition, there is almost always a "so what happens here?" The interviewer is checking whether the answer was understood or memorised. So prepare a second sentence for each of the eight — one failure mode, one trade-off, or one place you have seen it break in real code.

That second sentence is also what makes an answer sound like experience rather than revision. "Closures keep variables alive, which is why a long-lived callback can hold a large object in memory" is a better answer than "closures keep variables alive", and it takes one extra breath to say.

How to practise: 90 seconds, out loud, recorded

Reading the answers above will not make you able to say them. Speaking them will. The method:

  1. Answer aloud in 90 seconds. Phone on the table, recording. No notes, no scrolling. Ninety seconds is roughly one answer plus one follow-up — the length of a real answer.
  2. Listen back and ask three questions. Did I give the definition before the example, or did I ramble into an example first? Did I say "it depends" without saying what it depends on? Did I stop at the definition, leaving no room for a follow-up?
  3. Write one line per question in a log: the question, your opening sentence, and whether the follow-up caught you. The log is the revision list — the questions that caught you are the only ones worth another pass.
  4. Do the eight, then widen. Eight answers spoken properly are worth more than 150 read once. Once the eight are fluent, work through a larger question bank and add the ones that catch you to the same log.
  5. Do at least one out loud to a person if you can — a friend, a colleague, anyone who will ask "why?". Speaking to a person is a different skill from speaking to a phone, and the interview is the former.

What to say when you do not know

You will get a question you cannot answer. What you do next is being assessed, and there is a version that scores:

  • Say that you do not know, then say how you would find out. "I have not used that in production. I would check whether it is a microtask or a macrotask first, because that decides the ordering — I would write a four-line test and log it." That is a better answer than a confident guess, because the guess is the thing the follow-up is designed to catch.
  • Ask a clarifying question if the question is ambiguous. "Which runtime?" or "Do you mean at definition time or call time?" is not stalling — it is the same instinct that stops you writing the wrong fix.
  • Reason from what you do know. Name the mental model you would test and the smallest experiment that would settle it. Interviewers hire people who can be wrong out loud and then correct themselves.
  • When you are corrected, restate the correction in your own words. "So the promise callback runs before the timer because it is a microtask — got it." That closes the loop and shows the correction landed.
